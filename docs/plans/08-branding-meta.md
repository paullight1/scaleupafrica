# 08 — Branding & Meta: remove all Lovable traces, real metadata, OG banner, README

> Source of truth: `docs/plans/00-FOUNDATION.md` (§1 tokens, §3 imagery/OG, §6 branding removal — **locked**).
> This plan is a spec for an implementation agent. Plan only — no code has been changed yet.

## Goal

Zero Lovable branding anywhere a user, crawler, or contributor can see it. The app gets:
real homepage-derived `<title>`/meta/OG/Twitter tags, a 1200×630 social banner authored to the
new navy/orange theme, a real favicon set (icon + apple-touch + webmanifest), a `<SEO>` route
helper, a real README, a renamed package, Lovable dependencies removed (including the OAuth
broker, replaced by native Supabase Google OAuth), robots/sitemap, and a branded NotFound.

## Scope

**In:** `index.html`, `public/*` (favicon set, og-banner, robots, sitemap, webmanifest),
`README.md`, `package.json` + lockfiles, `vite.config.ts`, `src/integrations/lovable/` (delete),
`src/pages/Auth.tsx` (OAuth swap), `src/components/common/SEO.tsx` (new) + wiring into all
existing pages, `src/pages/NotFound.tsx`, `CLAUDE.md` (stale Lovable references), one-off banner
generation script.

**Out (owned elsewhere, coordinated below):**
- Theme tokens / primitives / fonts — plan 01 (we consume `--navy`, `--primary`, Sora).
- Per-profile dynamic OG for `/directory/:slug` — plan 04 (consumes our `<SEO>`).
- `/dashboard` page itself — plan 03 (we specify its SEO entry; plan 03 wires it).
- `supabase/functions/aggregate-funding` `LOVABLE_API_KEY` / `ai.gateway.lovable.dev` — this is
  a **functional AI gateway**, not branding; invisible to users. Migrating it to a direct
  Gemini/OpenAI key belongs to plan 05/07. This plan does NOT touch it, and the acceptance grep
  explicitly carves it out (see §9).

### 6b. `@lovable.dev/cloud-auth-js` — **decision: REPLACE, then remove**

**Why it exists:** `src/integrations/lovable/index.ts` wraps `createLovableAuth()`: it redirects
the browser through **Lovable's hosted OAuth broker** (their Google OAuth client), receives
Supabase-compatible tokens back, and calls `supabase.auth.setSession(tokens)`. Only consumer:
`src/pages/Auth.tsx:65` (`handleGoogle`).

**Why replace rather than keep:** (1) it is itself branding — the Google consent screen and
redirect chain show Lovable, exactly what this plan must remove; (2) hard runtime dependency on
a third-party's free broker staying up and on their Google quota; (3) `.env` shows the Supabase
project is a plain `https://<id>.supabase.co` project **we control**, so native
`supabase.auth.signInWithOAuth` is fully available; (4) it blocks deleting the package and the
`src/integrations/lovable/` directory.

**Safe migration path (ordered — auth must not break):**
1. **Prereq (dashboard, before any code ships):** create a Google OAuth client in Google Cloud
   Console (Web application; authorized redirect URI = `https://<project-id>.supabase.co/auth/v1/callback`).
   In Supabase Dashboard → Authentication → Providers → Google: enable, paste client ID +
   secret. Add site URL + `http://localhost:8080` to Supabase Auth **Redirect URLs** allowlist.
   *This is configuration the implementation agent must flag for a human if it lacks dashboard access — do NOT merge step 2 before this is confirmed.*
2. Edit `src/pages/Auth.tsx`:
   - line 4: delete `import { lovable } from "@/integrations/lovable/index";`
   - `handleGoogle` becomes:
     ```ts
     const handleGoogle = async () => {
       setBusy(true);
       const { error } = await supabase.auth.signInWithOAuth({
         provider: "google",
         options: { redirectTo: `${window.location.origin}${next}` },
       });
       if (error) {
         toast.error("Google sign in failed. Please try again or use email.");
         setBusy(false);
       }
       // on success the browser redirects; no further code runs
     };
     ```
     (`next` is the existing post-auth destination variable already used by the email flow;
     reuse it so both flows land in the same place. `supabase` is already imported in Auth.tsx.)
   - Session pickup needs no work: `useAuth`'s `onAuthStateChange` + `persistSession` handle the
     callback redirect exactly as it handles email sign-in.
3. Delete `src/integrations/lovable/index.ts` and the now-empty `src/integrations/lovable/` dir.
4. `npm uninstall @lovable.dev/cloud-auth-js` (and `bun remove` — see lockfiles below).
5. **Verify before merge:** manual Google sign-in on localhost:8080 → lands signed-in; sign-out;
   email flow unaffected; `npm run build` green.
6. Rollback plan: steps 2–4 are one commit; revert restores the Lovable broker (package still in
   git history). Do the swap in its own PR/commit for this reason.

## 8. `<SEO>` component + per-route titles/meta

**Ownership decision (stated per Foundation §2):** **Plan 08 owns the `<SEO>` primitive** —
its API, file, and implementation land with this plan at `src/components/common/SEO.tsx`.
Plan 01 lists it in the primitive inventory but must NOT implement a competing one; if plan 01
is implemented first, it leaves a stub reference to this spec. **Plan 04 consumes it** for
`/directory/:slug` (per-profile title/OG values) and separately owns crawler-visible dynamic OG
(prerender/edge). Plan 03 consumes it for `/dashboard`.

**Approach: react-helmet-free** (no new dependency). A small component that, in a
`useEffect`, sets `document.title` and upserts meta tags by `name`/`property`, restoring
nothing on unmount (last-write-wins per route is correct for an SPA).

**Files:**
- `src/lib/seo.ts` — constants: `SITE_NAME`, `SITE_URL` (same TODO token as §2),
  `DEFAULT_DESCRIPTION`, `DEFAULT_OG_IMAGE = \`${SITE_URL}/og-banner.png\``, and
  `buildTitle(page?: string)` → `page ? \`${page} | Cresciva\` : DEFAULT_TITLE`.
- `src/components/common/SEO.tsx`:
  ```ts
  type SEOProps = {
    title?: string;        // page part only; component appends " | Cresciva"
    description?: string;  // defaults to DEFAULT_DESCRIPTION
    image?: string;        // absolute URL; defaults to DEFAULT_OG_IMAGE
    canonicalPath?: string;// e.g. "/directory"; sets <link rel=canonical> + og:url
    type?: "website" | "article" | "profile"; // og:type, default "website"
    noindex?: boolean;     // upserts <meta name="robots" content="noindex"> (auth/admin/404)
  };
  ```
  Behavior: `document.title = buildTitle(title)`; upsert `meta[name=description]`,
  `og:title|description|type|url|image`, `twitter:title|description|image|card`;
  upsert/replace `link[rel=canonical]` from `SITE_URL + canonicalPath`. Re-runs when props
  change (covers `:slug` param changes).
- **Test** `src/components/common/SEO.test.tsx` (Vitest/jsdom): renders → `document.title`
  correct; description upserted not duplicated; noindex adds robots meta; prop change updates
  tags.
