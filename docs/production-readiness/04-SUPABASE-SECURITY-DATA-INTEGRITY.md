# Supabase Security, Data Integrity & Recovery Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Prove that Cresciva's production Supabase schema enforces least privilege, preserves data integrity, supports recoverable operations, and cannot expose privileged mutations or personal contact data through unintended API paths.

**Architecture:** Keep Supabase Postgres as the authoritative datastore. Validate the full RLS/GRANT/function/storage boundary with repeatable tests, run Supabase security/performance advisors, close material findings through timestamped migrations, add backup/restore evidence, and define data-retention/deletion behavior.

**Tech Stack:** Supabase Postgres, RLS, Storage, Auth, Edge Functions, SQL migrations, generated TypeScript types, pgTAP/SQL integration tests or the current Supabase-supported DB test runner.

**Spec:** `docs/superpowers/specs/2026-08-20-cresciva-production-readiness-design.md`

## Global Constraints

- Read current Supabase changelog/docs before implementation because CLI/security behavior changes over time.
- Every table in an exposed schema must have RLS enabled unless access is intentionally impossible through grants and documented.
- `SECURITY DEFINER` functions must either perform explicit caller authorization or be inaccessible to browser roles.
- Never use user-editable `user_metadata` for authorization.
- Frontend receives only publishable Supabase keys.
- Database changes are authored as migrations generated by the Supabase CLI, not hand-invented timestamps.
- Live production data is never copied into committed test fixtures.

**Files:**

**Interfaces:**

- [ ] **Step 1: Inventory exposed objects**

Include at minimum:

```text

```

- [ ] **Step 2: Define expected permissions in the evidence document**

Example matrix entries:

| Object | anon | authenticated owner | authenticated other | admin | service_role |
| --- | --- | --- | --- | --- | --- |
| public profile safe columns | read active | read | read | read | full |
| raw email/phone/whatsapp columns | no bulk read | own/edit path only | no bulk directory exposure | operational access only | full |
| subscription | none | read own | no | admin support if explicitly designed | full |
| payment | none | read own | no | support/reconciliation only | full |
| webhook event payload | no | no | no | sanitized/support view only | full |

Do not accept “authenticated” as authorization by itself for owner-scoped data.

- [ ] **Step 3: Write executable negative tests**

Tests must prove forbidden operations fail, including:

- anon selecting raw profile contact columns;
- user A reading/editing user B's private profile/payment/subscription rows;
- browser roles inserting/updating `subscriptions` or `payments` directly;
- anon/authenticated invoking service-only `grant_annual_access`;
- anon invoking `admin_set_role`;
- non-admin authenticated user changing roles;
- user uploading profile media outside their UID path.

- [ ] **Step 4: Write positive tests**

Prove legitimate own-row edit/read, public safe profile read, opt-in contact reveal, admin authorized operations and service settlement paths continue to work.

### Task 2: Audit every `SECURITY DEFINER` function

**Files:**
- Modify: affected SQL migrations only through new corrective migration(s)
- Update: `docs/production-readiness/evidence/supabase-security-review.md`

- [ ] **Step 1: Query all security-definer functions in exposed schemas**

For each function record:

- schema/name/signature;
- `search_path` configuration;
- roles with EXECUTE;
- whether it checks `auth.uid()`/admin authorization internally;
- whether service-role-only is more appropriate.

- [ ] **Step 2: Enforce one of two safe patterns**

**Browser-callable privileged RPC:** explicit caller auth/authorization inside function + restricted EXECUTE grants.

**Internal/service RPC:**

```sql
REVOKE EXECUTE ON FUNCTION public.some_function(...) FROM PUBLIC, anon, authenticated;
GRANT EXECUTE ON FUNCTION public.some_function(...) TO service_role;
```

- [ ] **Step 3: Specifically re-verify**

```text
has_active_subscription
handle_new_user
admin_set_role
grant_annual_access
directory_facets
get_profile_contact
increment_profile_views
```

The historical migrations already harden several of these; tests prove that current production schema matches the intended final state.

### Task 4: Verify schema/index/query integrity

**Files:**
- New migrations as needed
- Modify: `Backend/src/db/schema.ts` or the repository's current Drizzle schema mirror when drift is discovered
- Regenerate: `Shared/src/integrations/supabase/types.ts` or the current generated-types path

- [ ] **Step 1: Compare live schema with migration history and Drizzle mirror**

No production-only column/table/function may remain undocumented in migrations.

- [ ] **Step 2: Generate current Supabase TypeScript types**

Use the verified Cresciva project ID and compare generated output. Remove temporary casts only when the generated schema actually supports the type.

- [ ] **Step 3: Check critical query plans**

Use `EXPLAIN (ANALYZE, BUFFERS)` on representative non-sensitive test data for directory search, slug lookup, payment reference lookup, user payment history, funding cache and email throttle queries.

Do not run expensive unbounded production `ANALYZE` experiments during peak traffic.

- [ ] **Step 4: Add missing indexes only when justified by query shape**

Prefer focused composite/partial indexes instead of speculative indexing every column.

## Phase 4 Definition of Done

- Authorization matrix has executable positive and negative tests.
- Every exposed table has deliberate RLS/grant treatment.
- Every `SECURITY DEFINER` function has verified authorization and EXECUTE grants.
- Security advisors have no unresolved critical/high findings.
- Performance advisors are reviewed and launch-critical findings handled.
- Live schema, migrations, generated types and Backend schema mirror agree.
- Storage lifecycle/policies are tested.
- Retention/deletion behavior is explicit.
- Backup/restore is rehearsed and evidenced.
- Evidence ends with `PHASE 4 RELEASE GATE: PASS`.
